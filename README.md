# TableTap

A mobile-first restaurant guest experience. The guest page includes a restaurant
menu, Wi-Fi details, private feedback, and a digital loyalty card. Loyalty
enrollment and wallet pass generation are included; stamp awarding is deferred
until the admin phase.

## Run locally

```bash
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). The root route redirects to
the demo restaurant at `/juniper-and-rye`; the restaurant page remains available
at both `/<slug>` and `/r/<slug>`.

Without Supabase credentials the app serves the included demo restaurant and
menu. To connect a Supabase project:

1. Copy `.env.example` to `.env.local`.
2. Set `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and the
   server-only `SUPABASE_SERVICE_ROLE_KEY`.
3. Run [`supabase/schema.sql`](./supabase/schema.sql) in the Supabase SQL editor.
4. Configure Apple and/or Google Wallet credentials below.
5. Restart the development server and open `/juniper-and-rye`.

The schema creates restaurants, menus, feedback, loyalty, guest links, page
views, and rate-limit storage; seeds the demo restaurant; and enables row-level
security. Published guest pages are public; restaurant administrators are scoped
to their own restaurant data. Feedback is written through the rate-limited server
endpoint and is not readable by guests. Configure each restaurant's `wifi_ssid`,
`wifi_password`, and `google_review_url` fields in Supabase. Wi-Fi details are
intentionally shown to guests of that published restaurant.

To update an existing project, run the current [`supabase/schema.sql`](./supabase/schema.sql)
in the Supabase SQL editor. It is designed to be re-run and adds the current
columns, tables, functions, grants, and row-level policies without replacing
existing menu data. Keep service-role credentials on the server only.
Alternatively, apply [`supabase/migrations/20261028134200_table_level_guest_support.sql`](./supabase/migrations/20261028134200_table_level_guest_support.sql)
to an existing installation to add table-specific guest destinations and table
attribution for feedback, loyalty enrollments, and page views.

## Wallet pass setup

Wallet passes require merchant credentials; enrollment still creates a digital
card when wallet credentials are not configured.

### Apple Wallet

1. Create a Pass Type ID and matching signing certificate in the Apple Developer
   account. Download the Apple WWDR certificate.
2. Base64-encode the WWDR certificate, Pass Type ID certificate, and signing
   private key, then set `APPLE_WWDR_CERT_BASE64`,
   `APPLE_SIGNER_CERT_BASE64`, and `APPLE_SIGNER_KEY_BASE64`. Set the matching
   `APPLE_PASS_TYPE_IDENTIFIER` and `APPLE_TEAM_IDENTIFIER`; set
   `APPLE_SIGNER_KEY_PASSPHRASE` if the private key is encrypted.
3. Keep all certificate/key values in deployment secrets or `.env.local`; never
   commit them.

The signed `.pkpass` is generated by
[`src/app/api/loyalty/pass/apple/route.ts`](./src/app/api/loyalty/pass/apple/route.ts)
using the pass definition and icons in [`wallet/apple/`](./wallet/apple/).

### Google Wallet

1. Set up a Google Wallet issuer and enable the Google Wallet API for its
   service account.
2. Create a Generic loyalty class for the issuer in the Google Wallet console.
   Set `GOOGLE_WALLET_CLASS_ID` to its full ID (`issuerId.classSuffix`).
3. Set `GOOGLE_WALLET_ISSUER_ID`, `GOOGLE_WALLET_CLASS_ID`,
   `GOOGLE_WALLET_SERVICE_ACCOUNT_EMAIL`, and
   `GOOGLE_WALLET_PRIVATE_KEY`. Store the PEM key with `\n` line breaks in
   deployment secrets.

The enrollment endpoint signs a Google Wallet save URL for each member. The
card starts at 0/5 stamps. Restaurant admins can award stamps from the
dashboard; updated progress appears on newly generated passes.

## Authentication and account setup

Restaurant owners can create an account at `/admin/signup`. Supabase email
confirmation must be enabled for production; new users receive a verification
link before they can access the dashboard or onboarding. Configure the Supabase
Auth Site URL and redirect allow list for the production origin and
`/auth/callback` (plus localhost for local development). Configure production
SMTP so verification and password-reset email delivery is reliable. Passwords
must contain at least 12 characters in the TableTap signup/reset forms.

Sign-in, signup, password reset, and logout are handled through server routes
with Supabase SSR cookies. `/admin`, admin APIs, and `/onboarding` require a
verified Supabase Auth user; restaurant admin APIs also check the user's
`restaurant_admins` membership. Configure `NEXT_PUBLIC_SITE_URL` to the exact
canonical HTTPS origin used in Supabase redirect settings.

Account settings in the dashboard allow the user to request a password reset
and delete their own account after re-entering their password and typing
`DELETE`. Deletion removes restaurants and related guest data when that user is
the only administrator. Shared restaurants remain for their other admins.

New verified accounts enter the four-step onboarding at `/onboarding`: restaurant
details, an optional first menu item, Wi-Fi details, and a generated QR code.
The restaurant remains unpublished until the user publishes the guest page at
the final step.

## Admin dashboard setup

The protected dashboard is available at `/admin`; sign in at `/admin/login`
using a Supabase Auth email/password account. The server uses the Supabase
service-role key only after validating the user's Auth session and their
`restaurant_admins` membership. Never expose `SUPABASE_SERVICE_ROLE_KEY` as a
`NEXT_PUBLIC_` variable.

To grant a restaurant manager access:

1. Create or invite the user in Supabase Authentication.
2. Copy that user's Auth UUID and the restaurant UUID from the `restaurants`
   table.
3. Run the following SQL in the Supabase SQL editor, replacing the UUIDs:

```sql
insert into public.restaurant_admins (restaurant_id, user_id)
values ('RESTAURANT_UUID', 'AUTH_USER_UUID')
on conflict do nothing;
```

Add the account to another restaurant's membership row to enable switching
between those restaurants. Manager membership is intentionally provisioned
manually; staff accounts and role management are not part of this phase.

The dashboard includes restaurant-scoped menu and settings management, table
management, recent private feedback, loyalty member counts, and QR/NFC guest
links. The Tables section creates unique destinations at `/t/<code>`, supports
individual and bulk table creation, activation, edits and deletion, and offers
downloadable high-resolution PNG and SVG QR codes. NFC tags should be written
with the same table-specific guest URL. The older `/go/<token>` and
restaurant-level guest routes continue to work. Set `NEXT_PUBLIC_SITE_URL` to
the canonical public origin when creating links in deployments behind a proxy.

The Analytics section reports guest page opens, loyalty joins, feedback volume,
average rating, and high-rating review prompts across the selected date range.
Guest page opens are approximate views (repeat visits and automated traffic may
be included). Feedback can be filtered, reviewed, and marked resolved. Loyalty
members are listed with progress; staff can add stamps up to the five-stamp
reward goal. Stamp changes are recorded immediately and show on newly generated
Apple passes.

Run the current `supabase/schema.sql` in the SQL editor to add page-view events,
feedback table/resolution/prompt metadata, and the restricted analytics/stamp
functions, tenant-scoped admin policies, and the durable rate-limit function.
Existing historical feedback and page views remain intact; page-view tracking
begins after this schema is installed. The server-side rate limiter hashes
request IP addresses and stores only those hashes and short-lived counters.
Rate-limit checks fail closed if the Supabase function is unavailable.

## Analytics, error monitoring, and backups

Vercel Analytics is mounted in the app and tracks non-sensitive events such as
sign-in, signup, feedback submission (rating only), and loyalty enrollment.
Enable Web Analytics in the Vercel project to receive events. Sentry is wired for
client, server, edge, and Next.js request errors; set `NEXT_PUBLIC_SENTRY_DSN`
and `SENTRY_DSN` to enable reporting. The public DSN is an ingest identifier,
not an API secret. Optionally set the server-only `SENTRY_AUTH_TOKEN`,
`SENTRY_ORG`, and `SENTRY_PROJECT` during builds to upload source maps. Error
events have query strings, request bodies, cookies, authorization headers,
set-cookie headers, and user identity removed before sending.
Analytics and Sentry are disabled when their DSNs/project integrations are not
configured.

The current dependency audit still reports a high-severity `node-forge`
advisory through `passkit-generator`; npm reports no upstream fix yet. Apple
Wallet signing uses deployment-controlled certificates and keys, never
guest-supplied certificate data. Recheck `npm audit` and update the Wallet
dependency as soon as a patched release is available.

Enable automated database backups in the Supabase project dashboard and verify
the retention period available on the selected plan. For production, assess
Point-in-Time Recovery (PITR) and regularly test restoring a backup into a
separate project. Keep periodic exports outside the production database and
restrict access to backup files. A backup is not verified until a restore test
has succeeded.

`/privacy` and `/terms` contain starter notices linked from the guest and admin
experiences. They are not legal advice; have qualified counsel adapt them with
the operator's contact details, applicable jurisdictions, data-retention rules,
and final service-provider configuration before launch.
